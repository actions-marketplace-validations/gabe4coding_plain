# Performance

These results are measurements on a small set of workflows. They are not a guarantee for your site. The
[benchmark reports](#benchmark-reports) give the method, the raw data and the commands to run them again.

## Agent cost and speed against Playwright MCP

A main agent did six synthetic browser workflows with plain and with Playwright MCP 0.0.82. Each workflow
ran three times with each of three main models: 108 trials in total.

| Main model | API cost per task: plain / Playwright MCP | Cost change | Mean seconds: plain / Playwright MCP | Time change |
|---|---:|---:|---:|---:|
| GPT-5.6 Luna (small) | $0.001344 / $0.001262 | +7% | 17.0 / 35.4 | −52% |
| GPT-5.6 Terra (medium) | $0.010184 / $0.013374 | −24% | 17.0 / 22.9 | −25% |
| GPT-6 Astra (top) | $0.044577 / $0.049695 | −10% | 20.4 / 41.8 | −51% |

- The costs include the main agent and Jev, with caching, recovery and verification.
- For Luna and Astra, the 95% cost interval includes parity. Only the Terra saving is clear (0.66–0.91×).
- Results change by task. Astra account editing cost 20% more. Terra catalog browsing was 54% slower.
- The main agent made 19% fewer calls (333 against 412).
- The times include provider latency and the page wait behavior of each stack.
- Both stacks completed all 54 tasks. Three repetitions for each workflow and model are not sufficient to show
  production reliability.

Full results: [current browser comparison](benchmarks/current-browser-comparison.md) and the
[full report and audit](benchmarks/2026-09-21-current/README.md). The
[protocol](benchmarks/browser-workflows.md) tells how to run the comparison again.

## Step time

The comparison above was measured before two changes to the step time. Each change was measured on the runnable
examples (spec runs) and on an agent-style MCP session with 5 s between calls.

| Change | Spec runs | MCP session |
|---|---:|---:|
| [Speculative Jev calls, network-aware settle, warm connections](benchmarks/step-overhead.md) | −43% overhead | −43% tool time |
| [Shorter settle, click holds](benchmarks/browser-step-time.md) | −10% overhead | −9% overhead |

Overhead is the step time minus the time of the page action itself. After the first change, a warm `step` call
took approximately 250–290 ms in place of 620 ms. Desktop and mobile steps also became faster, mostly because the
Jev connections stay open between steps.

What this means for your runs:

- The Jev round trip is the minimum time of a step that asks Jev. Only a nearer API region makes it shorter.
- Each spec gets a new browser context. Thus the first `goto` of each spec is slower than the next ones.
- For a large suite, `--workers N` gives the largest gain. Refer to [running suites](running.mdx).
- The settle wait cannot see timers. For content that comes later, use a `wait` step.
