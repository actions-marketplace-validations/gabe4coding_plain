# Development

This page is for contributors. To use plainwright, start with [getting started](getting-started.mdx).
[CLAUDE.md](../CLAUDE.md) describes the architecture and the code conventions.

## Build and test

```sh
npm ci
npx playwright install chromium
npm run build    # compile src/ to dist/ and make the plugin runtime archives again
npm test         # build, then run the tests in dist/**/*.test.js and scripts/*.test.mjs
npm run check:docs
npm run test:mods  # the session pane mod tests (claude plugin test). Needs the claude CLI. Not in npm test
npm run verify   # the key-free gate: tests, docs, examples and plugin install
```

`npm run verify` runs `npm test`, `npm run check:docs`, `npm run check:examples` and `npm run test:plugins`. The
CI workflow runs the same command.

`npm run check:examples` validates the specs in `examples/`, `examples/mobile/` and `e2e/`. It also validates
each full spec and config example in the user docs, with the CLI of its engine.

`npm run check:docs` checks the user docs: README.md, `docs/*.mdx` and `examples/mobile/README.md`. Each file must
compile as MDX and show correctly on GitHub. The text must follow the ASD-STE100 rules that a script can test, for
example a maximum of 25 words in a sentence. All relative links and anchors must resolve. The CI workflow runs the
same check. The full writing rules are in `CLAUDE.md`, in the section "Documentation".

`npm test` needs no API key and no native SDK. It runs these tests:

- The browser runner against headless Chromium, with `data:` URLs.
- The desktop and mobile sessions, with injected adapters and injected Jev decisions.
- Mobile requests from real WebdriverIO to a local Appium-protocol fixture, for Android and iOS.
- MCP recording and replay of the saved specs.
- The pre-PR hook, in a temporary repository with a git worktree.

The session pane mod in `mods/session-pane/` has its own tests. `npm run test:mods` runs them with
`claude plugin test`. If Anthropic disables installed mods for your account, the command prints a notice and
returns exit code 0, but no test runs. The build copies the mod into each plugin, without the tests.

These tests do not prove that a real device, simulator or desktop works. For that, use the
[native smoke tests](#verification).

## Validation before a pull request

Before you open a pull request, run the full validation loop:

```sh
node scripts/validate.mjs
```

The script stops at the first failure. In order, it runs:

1. `npm run verify`.
2. The live e2e suite, `node scripts/e2e.mjs`.
3. The claims gate, `node scripts/benchmark-claims.mjs --gate`. A false pass fails it.
4. The agent evals, `node scripts/eval-agent.mjs`, when the MCP tools, their results or the browser skill
   changed.

At the end, it lists the benchmarks that the changed files need. Compare each one with a run on main. The
`validating-changes` skill in `.claude/skills/` gives the full procedure, also for the review of the code and
the docs. Codex reads the same skill from `.agents/skills/`.

A hook in `.claude/settings.json` and `.codex/hooks.json` stops `gh pr create`. It lets the command run only
when `scripts/validate.mjs` passed on the same files as HEAD. The hook checks the checkout where the command
runs, also in a git worktree.

### Live e2e suite

The live checks need a Jev key. They use no remote site. `e2e/site.mjs` serves all the pages on `127.0.0.1`
from the process of the runner. Thus a failure comes from plainwright or Jev, not from the network.

- Each `e2e/*.yaml` spec must pass. A spec with the tag `expect-fail` must end `fail`. A pass there is a false
  pass.
- A spec that passes only on a retry counts, but the runner lists it as flaky.
- The runner also records a login through the MCP server and runs the saved spec again.

To run one spec, use `node scripts/e2e.mjs --only forms`.

### Browser exploration

Run measured MCP flows against disposable local sites with a Jev key:

```sh
node scripts/autoresearch-web.mjs --runs 3 --out /tmp/research.json
```

The report records each call, its elapsed time, Jev tokens and independent DOM checks.
The flows cover login, forms, frames, editors, inert backgrounds and disabled fieldsets.
An unexpected result makes the command fail.
Use `--cli /path/to/dist/cli.js` for a baseline build.
Use `--observe` to record findings without a failed exit status.

### Agent evals

`node scripts/eval-agent.mjs` gives tasks on the local site to a real `claude -p` agent and a real `codex exec`
agent. It grades each run:

- The final answer must contain the text that the page shows.
- The agent must reach the page only through the plainwright tools, with no failed tool call.
- The number of tool calls must stay in the budget of the task.
- A spec that the agent saves must pass when the CLI runs it.

Each agent runs isolated from your own setup, with the skill and the MCP server of the checkout. The evals cost
Claude and Codex usage. CI does not run them. Use `--agent claude` or `--only login` to run fewer.

### Continuous integration

- The `Test` workflow runs `npm run verify` on each pull request and on main. It then checks that `dist/` and
  the runtime archives match the build.
- The `Live` workflow runs the e2e suite and the claims gate. It runs on pull requests that change the runtime,
  the e2e suite or the eval data. It needs the `TYPESAFE_API_KEY` repository secret. Without it, the workflow fails, but
  on a pull request from a fork it is skipped.

To run one test file or one test case after a build:

```sh
node --test dist/browser/runner.test.js
node --test --test-name-pattern "<name>" dist/jev/pick.test.js
```

## Committed build output

The repository contains `dist/` and the three `runtime.tgz` archives. The plugins ship this built output, and
`bin/plainwright.mjs` runs `dist/cli.js` directly.

- After a change in `src/`, run `npm run build` before you commit. Then `dist/` agrees with the source.
- Do not edit the generated files by hand: `dist/`, `plugins/*/runtime.tgz`, `plugins/*/bin/launch.mjs`.
- The CI workflow runs `npm run verify`. Then it fails if `dist/` or an archive is different from the build output.
- Git ignores the compiled tests, `dist/**/*.test.js`.

## Repository layout

```text
package.json                 all dependencies, the three CLI binaries, build and test scripts
src/                         browser, desktop, mobile and shared code, with tests next to each module
dist/                        compiled runtime (committed)
bin/                         CLI launchers
plugins/
  plainwright/               browser plugin: manifests, skill, launcher, runtime archive
  plainwright-computer/      desktop plugin
  plainwright-mobile/        mobile plugin
scripts/                     plugin build, smoke tests, benchmarks, evals, the validation loop
e2e/                         the live e2e suite: its local site and specs
examples/                    browser specs against public demo sites; examples/mobile/ for mobile
docs/                        user documentation; docs/benchmarks/ for benchmark reports
```

## Plugin packaging

One root `package.json` and one `package-lock.json` own the dependencies of all engines. Do not add a package
manifest, a lockfile, a symlink or a parent-directory import to a plugin.

Each plugin directory contains:

- The portable manifests `plugin.json` and `mcp.json`. The server starts in `${PLUGIN_ROOT}`.
- The Claude Code manifests `.claude-plugin/plugin.json` and `.mcp.json`. The server runs `${CLAUDE_PLUGIN_ROOT}/bin/launch.mjs`.
- The Codex manifest `.codex-plugin/plugin.json`. It uses the same `.mcp.json` and `skills/`.
- The skill in `skills/`.
- The generated `runtime.tgz`, `bin/launch.mjs` and `LICENSE`.

Keep the `name`, `version` and `description` equal in the three `plugin.json` files of each plugin. Both root
marketplaces, `.claude-plugin/marketplace.json` and `.agents/plugins/marketplace.json`, list the three plugin
directories.

`npm run build` compiles TypeScript. Then `scripts/build-plugins.mjs` packs one archive and copies it into each
plugin. The archive contains the root package manifest, the root lockfile as `npm-shrinkwrap.json`, the compiled
runtime without tests, the CLI launchers and the license. Thus a plugin install uses the locked dependency graph.

On the first start, the plugin launcher installs the archive in `plugins/<name>/.runtime/<archive hash>/`. A new
archive gets a new installation. The launcher writes npm output to stderr, because stdout is the MCP channel.
Git ignores the `.runtime/` folders.

To check the archives as a plugin host sees them, run:

```sh
npm run test:plugins
```

This script copies each plugin to a temporary folder, compares the three manifests, installs the archive and lists
the MCP tools. It needs no API key.

Pitfalls:

- Keep `.env` files and `.runtime/` folders out of the plugin directories. Codex copies the plugin directory into
  `~/.codex/plugins/cache/`.
- To try a plugin from a clone without an install, run `claude --plugin-dir /absolute/path/to/plainwright/plugins/plainwright`.
  Use the same command for `plugins/plainwright-computer` and `plugins/plainwright-mobile`.
- `AGENTS.md` is a symlink to `CLAUDE.md`. Codex reads the same repository guidance as Claude Code.

## Verification

The native smoke tests are opt-in. They run on a real desktop, device or simulator. Each test builds the project
first.

### Desktop on macOS

```sh
npm run test:computer:mac
```

The test compiles a disposable Cocoa application with `xcrun clang`, then removes it. Give the host that runs Node
the Accessibility and Screen Recording permissions. Without Screen Recording, add `-- --skip-screenshot`.

The test injects deterministic Jev decisions and needs no API key. It checks the real application state after
attach, tree capture, fill, click, check and uncheck, a key press, hover and a PNG screenshot. A second `check` on
a checked box must not change it.
Windows and Linux need the same kind of run on their own hosts before you claim native parity.

### Mobile connection

This test connects to your installed test app, reads the tree and takes a PNG screenshot. It needs no API key.

```sh
PLAINWRIGHT_MOBILE_PLATFORM=android \
PLAINWRIGHT_MOBILE_DEVICE=emulator-5554 \
PLAINWRIGHT_MOBILE_APP=com.example.fixture \
npm run test:mobile
```

| Variable | Meaning |
|---|---|
| `PLAINWRIGHT_MOBILE_PLATFORM` | `android` or `ios`. |
| `PLAINWRIGHT_MOBILE_DEVICE` | Device ID: ADB serial or UDID. |
| `PLAINWRIGHT_MOBILE_APP` | App package or bundle ID. |
| `PLAINWRIGHT_MOBILE_CAPABILITIES` | Optional. A JSON object of extra Appium capabilities. |
| `PLAINWRIGHT_APPIUM_URL` | Optional. The Appium server. Default `http://127.0.0.1:4723`. |

This test does not check taps, input or gestures.

### Android fixture

This test builds a small offline Android app, installs it, and does real text entry, check and uncheck, tap, long
press, scroll, swipe and screenshots. It records a flow through MCP, restarts the app and runs the saved spec. Then
it removes the app. If the fixture app is already installed, the test stops and does not replace it.

Prepare the host:

1. Install Android SDK Platform 36 and Build-Tools 36.0.0.
2. Set `ANDROID_HOME` (or `ANDROID_SDK_ROOT`) and `JAVA_HOME`.
3. Make sure that `zip` is on your `PATH`.
4. Start your emulator.
5. Start Appium with the UiAutomator2 driver.

You do not need Gradle or an application project.

```sh
PLAINWRIGHT_MOBILE_DEVICE=emulator-5554 npm run test:mobile:android
PLAINWRIGHT_MOBILE_DEVICE=emulator-5554 npm run test:mobile:android -- --live-jev
```

- The default run injects deterministic decisions. `--live-jev` uses real Jev picks and judgments, with your key
  from the repository `.env` or the user env file.
- At the end, the test prints a temporary folder with `recorded.yaml`, `report.json` and `preview.png`.
- To use a different installed Build-Tools version, set `PLAINWRIGHT_ANDROID_BUILD_TOOLS`.

This test checks native Android controls. It does not prove React Native or iOS parity.

### iOS Simulator fixture

This test builds an offline UIKit app with the Xcode simulator SDK and installs it. It records native actions
through MCP, restarts the app and runs the saved spec. Then it removes the app. If the fixture app is already
installed, the test stops. You do not need an Apple developer account.

Prepare the host:

1. Install Xcode and an iOS Simulator runtime, iOS 16 or newer.
2. Complete the first-launch setup of Xcode. Make sure that `xcode-select -p` shows a path in Xcode.
3. Install the Appium XCUITest driver before you start the Appium server.
4. Boot an iPhone simulator.

```sh
xcrun simctl list devices booted
PLAINWRIGHT_MOBILE_DEVICE=<simulator-udid> npm run test:mobile:ios
PLAINWRIGHT_MOBILE_DEVICE=<simulator-udid> npm run test:mobile:ios -- --live-jev
```

- The first session builds WebDriverAgent. This can take some minutes. The test allows 4 minutes for each Appium
  request.
- Set `PLAINWRIGHT_APPIUM_URL` if your server uses a different address or port.
- At the end, the test prints a temporary folder with `recorded.yaml`, `report.json` and `preview.png`.
- The fixture closes its keyboard with its Done key. A generic `press: HideKeyboard` can fail on iPhone.

A pass on the simulator does not prove physical iPhone or React Native parity.

## Performance checks

The benchmark scripts need live sites and an API key. Build first, then compare a change against a saved run:

```sh
node scripts/benchmark-steps.mjs --runs 3 --out /tmp/new.json --compare /tmp/base.json
node scripts/benchmark-mcp.mjs --cli dist/cli.js --gap 5000 --runs 2
```

`benchmark-steps.mjs` reports the step overhead for each phase: the step time minus the page action time.
`benchmark-mcp.mjs` times an agent-style MCP session, with think time between calls.

Each area of the product has its own benchmark or eval:

```sh
node scripts/benchmark-planner.mjs --runs 3          # sentence → steps planner vs scripts/planner-cases.json
node scripts/benchmark-picks.mjs --runs 3            # picks with/without goal on saved pages (scripts/pick-states/)
node scripts/benchmark-agent.mjs --runs 3            # a real claude -p agent, changed on vs off (costs Claude usage); --read both: read on vs off
node scripts/benchmark-read.mjs --runs 2 --smart     # read vs smart snapshot on saved pages (scripts/read-states/, read-cases.json)
node scripts/eval-browser-steps.mjs --variant v1     # step-time eval: examples + MCP session, overhead and same step statuses (.claude/hillclimb/, gitignored)
node scripts/benchmark-claims.mjs --runs 3           # expect judging on saved pages (scripts/claim-cases.json); false passes must stay 0
node scripts/benchmark-pick-cache.mjs --skip turing-click   # pick cache on stale saved pages; wrong/unconfirmed hits must stay 0
node scripts/benchmark-steps.mjs --picks on --dir <scratch copy of examples>   # warm pick cache; never --dir examples
```

Change the desktop planner only when `benchmark-planner.mjs` shows an improvement. [Performance](performance.mdx)
summarizes the results.

## Documentation changes

If you change step kinds, thresholds, MCP tools, the env file loading or the plugin install steps, change the
matching doc in the same commit. For thresholds and tool names, also change the plugin skill.
