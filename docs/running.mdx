# Running suites

The three CLIs `plain` (browser), `plain-computer` (desktop) and `plain-mobile` (mobile) share
the options on this page:

```sh
plain --headless --workers 4 --retries 1 --tag smoke tests/
plain-computer --retries 1 tests/desktop/
plain-mobile 'tests/mobile/**/*.yaml'
```

[Reporting](reporting.mdx) describes the output formats. [Artifacts](artifacts.mdx) describes screenshots,
traces and debug files. [CI and containers](ci.mdx) shows the GitHub Action, GitLab and Docker.

## Choose the files

Each input is a spec file, a folder or a quoted glob. A folder gives every `.yaml` and `.yml` file in it and in
all its subfolders, hidden folders and `node_modules` included. In a glob, `*` matches in one folder and `**`
matches across folders.

The CLI sorts the files of each input and keeps the inputs in the order you give them. A path to a file that does
not exist becomes a load error. A glob that matches no file adds nothing. If you give no paths and the
[config file](#configuration) has no `files` key, the CLI prints a usage line and exits with code `2`. There is no
`--help` option.

Keep included flow files outside the paths that you run. A flow file has only `steps:`, so it gives a load error.

A spec that does not load (bad YAML, an incorrect field, an absent `$VAR`) is reported as `error`. It never runs,
plain does not retry it, and it does not count toward `--bail`. Selection filters do not hide it.

## Command-line options

Each option has a key with the same effect in the [config file](#configuration).

| Option | Config key | Default | What it does |
|---|---|---|---|
| Spec paths | `files` | None | The specs to run. Paths on the command line replace `files`. |
| `--headless` | `headless` | Window visible | Browser only. Hides the browser window. |
| `--timeout MS` | `timeout` | `15000` | Time limit for one action. Browser: `0` disables it. Desktop and mobile: must be more than `0`. |
| `--spec-timeout MS` | `specTimeout` | No limit | Time limit for one attempt of a spec. The spec `timeout:` field wins. |
| `--workers N` | `workers` | `1` | Browser specs that run at the same time, each in its own context. |
| `--retries N` | `retries` | `0` | Extra attempts after a result that is not `pass`. |
| `--bail [N]` | `bail` | `0` (off) | Stops new specs after N specs end without `pass`. `--bail` alone means `1`. |
| `--max-tokens N` | `maxTokens` | No limit | Stops new specs and retries when completed attempts used N tokens. |
| `--picks MODE` | `picks` | `on` | [Pick cache](#pick-cache) mode: `on`, `read` or `off`. |
| `--profile DIR` | `profile` | None | Browser only. Uses a persistent browser profile folder. |
| `--channel NAME` | `channel` | Bundled Chromium | Browser only. Uses an installed browser, for example `chrome`. |
| `--cdp URL` | `cdp` | None | Browser only. Attaches to a Chrome that runs with remote debugging. |
| `--server URL` | `server` | `http://127.0.0.1:4723` | Mobile only. The Appium server URL. |
| `--grep RE` | `grep` | None | Runs only specs whose name or path matches. |
| `--grep-invert RE` | `grepInvert` | None | Skips specs whose name or path matches. |
| `--tag T` | `tags` | None | Runs only specs that have this tag. Repeat it to require more tags. |
| `--last-failed` | None | Off | Runs only specs that did not pass in the previous run. |
| `--list` | None | Off | Prints the selected specs and runs nothing. |
| `--config FILE` | None | `plain.config.yaml` | Reads this config file. |
| `--reporter NAME[:FILE]` | `reporters` | Browser `text`, desktop and mobile `jsonl` | Output format. Repeat it for more outputs. |
| `--timing` | `timing` | Off | Browser only. Adds phase timings to `text` output. |
| `--artifacts DIR` | `artifacts.dir` | Off | Saves screenshots, traces and debug files in this folder. |
| `--screenshot MODE` | `artifacts.screenshot` | `on-failure` | Screenshot mode: `off`, `on-failure` or `always`. |
| `--trace MODE` | `artifacts.trace` | Browser `on-failure`, desktop and mobile `off` | Browser trace mode: `off`, `on-failure` or `always`. |

Numbers must be integers, except `--timeout`. `--workers`, `--max-tokens` and `--spec-timeout` must be more than
`0`. A browser-only option on the desktop or mobile CLI is an error (exit `2`). `--server` on the browser or
desktop CLI is also an error. The same keys in the config file do not stop the CLI. Read
[Desktop and mobile in the same folder](#desktop-and-mobile-in-the-same-folder). Desktop and mobile always use one worker. The browser also needs one worker with
`--profile` or `--cdp`. [Your real browser](agent-mode.mdx#your-real-browser) explains `--profile`, `--channel`
and `--cdp`.

The time to open the browser, app or device and the setup hook count toward `--spec-timeout`. Cleanup can
continue after the limit. [Timeouts](spec-reference.mdx#timeouts) describes what happens at the limit.

The CLIs also accept these commands in place of spec paths:

- `validate <paths>`: checks the specs and runs nothing. See [Check specs without a run](#check-specs-without-a-run).
- `mcp`: starts the MCP server for [agent mode](agent-mode.mdx). It reads no config file.
- `plan` and `do` (desktop only): see [one-sentence plan and do](computer-use.mdx#one-sentence-plan-and-do).

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Every reported spec passed (a flaky pass counts), or the selection is empty. |
| `1` | One or more specs ended `fail`, `inconclusive`, `error` or `skipped`, or a spec did not load. |
| `2` | The command is incorrect: unknown option, bad value, config error, no YAML file found, no API key, or a reporter or artifact setting that is not valid. |

An empty selection does not need an API key.

## Select specs

```sh
plain --grep 'Login|Checkout' tests/
plain --tag smoke --tag checkout tests/
```

`--grep` uses a JavaScript regular expression. It matches the spec name or the path relative to the current
folder. The match is case-sensitive. Put the expression in quotes to stop the shell from expanding it.

A spec must have all the tags that you give with `--tag`. Tag matches are exact and case-sensitive. In the spec,
`tags` is a string or a list, for example `tags: [smoke, checkout]`.

`--list` prints one line for each selected spec: the file, the name and the tags. It does not ask for an API key,
open a browser or run hooks:

```text
tests/checkout.yaml  Checkout with a saved address  [smoke, checkout]
```

## Retries and stop limits

If a spec passes on a retry, its status is `pass` and it is marked flaky. A flaky pass does not count toward
`--bail`. If all attempts fail, the spec keeps the status of the
last attempt.

`--bail` counts a spec only after its last retry. `--max-tokens` counts all completed attempts, failed attempts
and retries included.

Both limits stop only new work. Specs that run already finish, with their retries for `--bail`. Thus more than N
specs can fail, and a run can use more than N tokens. A spec that never starts gets the status `skipped`, with
the reason `bail` or `max-tokens`.

## Previous failures

Each completed run writes `.plain/last-run.json` in the current folder, with the final status of each spec.
Each run replaces it. All three CLIs share this file. Add `.plain/` to your `.gitignore`. `--list` and
`validate` do not change the file.

`--last-failed` keeps only the selected specs that did not pass in the previous run:

- If there is no file, or the file is not valid, plain runs all selected specs. It prints
  `no previous run found; running all selected specs`.
- If the previous run had no failures, plain runs nothing. It prints `no failures in the last run`.
- In all other cases, plain runs the selected specs whose final status was not `pass`. This includes
  skipped specs and load errors. Flaky passes are not included.

## Pick cache

A spec run remembers high-confidence picks. If the page did not change, the next run reuses the pick.
This avoids a new request to pick an element. Jev still judges claims (`expect`, `wait`) and classifies prompts.
The cache works for browser, desktop and mobile spec runs, not for agent mode (MCP).

| Mode | Behavior |
|---|---|
| `on` (default) | Uses stored picks and stores high-confidence picks of passed steps. |
| `read` | Uses stored picks and never writes a file. Use it in CI. |
| `off` | Does not use or write the cache. Jev picks each target. |

### Pick files

Each spec file gets a pick file next to it: `checkout.yaml` gets `checkout.picks.json`. An included flow
`flows/login.yaml` gets `flows/login.picks.json`, and all specs that include it share that file.

Commit the pick files with the specs. A diff shows which pick changed.
In CI, use `--picks read` to keep the working tree unchanged.

If the step text has a placeholder (`${env.*}` or `${hooks.*}`), the pick file holds only hashes. Other entries hold
the element description and the page address as plain text.

### When plain uses a stored pick

plain uses a stored pick only when:

- It is the first attempt of the spec. A retry always asks Jev.
- The page has the same origin and path. The query and the hash part of the address can change.
- The list of elements that Jev can pick from is the same. Element states (checked, selected, pressed, expanded,
  disabled) are part of the list. Typed field text does not change semantic browser picks.
- Spatial picks also require equal bounds of the candidates and an equal layout (text, values and bounds) of the reference elements.
- Exactly one element has the stored description.

A new row, a dialog over the page, or a button with a new name (`Subscribe` becomes `Unsubscribe`) causes a miss.
After a miss, Jev picks as usual. A step that used a stored pick has `(cached pick)` at the end of its detail and
`cached: true` in the JSON report.

### When entries change

- plain stores picks only from passed steps in a passed attempt, with confidence of at least 0.9.
  If the provider gives no confidence, plain uses the probability.
  A pick below 0.9 still acts at the pick threshold, but each run asks Jev again.
- plain never stores a pick of one of many identical elements (a target that ends with ` #2`), or a pick
  that Jev rejected.
- If an attempt does not pass, plain deletes the stored picks that it used. If the retry passes, its picks
  replace them. If a step that used stored picks does not pass, its detail names a debug file with these picks
  (`cache: <file>.json`).
- plain ignores a pick file from another Jev model, or from a version of plain with another element
  description format. The next passing run writes a new file.

To reset the cache, delete the pick file or one entry in it, or run once with `--picks off`. If you move a step to
a new position, it gets a new entry. The old entry stays in the file until you delete it.

[Pick cache benchmark](benchmarks/pick-cache.md) gives the measured savings.

## Configuration

Each CLI reads `plain.config.yaml` from the current folder, or
`plain.config.yml` if that file is absent. Use `--config FILE` to read another file. If that file does not
exist, the CLI stops with an error. `mcp` does not read a config file.

```yaml
files: ['tests/**/*.yaml']
headless: true
workers: 4
retries: 1
reporters:
  - text
  - junit:reports/junit.xml
  - {name: json, output: reports/results.json}
artifacts:
  dir: plain-results
  screenshot: on-failure
  trace: on-failure
```

In the config file, `tags` is a string or a list. `reporters` takes `NAME[:FILE]` strings or `{name, output}`
mappings.
`validate` does not use `files`: give it the paths.

### Paths and values

- Paths in the config file (`files`, `profile`, `artifacts.dir` and reporter files) are relative to the folder of
  the config file. This is also true with `--config`.
- A `profile` that starts with `~` starts in your home folder.
- Config values do not expand `$VAR`. Put secrets in the environment and use them in the spec `env` block.
- An unknown key, a wrong type or a number out of range stops the CLI with an error (exit `2`).

### Order of precedence

1. Command-line options.
2. The environment variables `PLAIN_PROFILE`, `PLAIN_CHANNEL`, `PLAIN_CDP` and
   `PLAIN_APPIUM_URL`. [Getting started](getting-started.mdx) lists all environment variables.
3. The config file.
4. The defaults.

`--tag` and `--reporter` on the command line replace the config lists. Each `artifacts`
key can be set alone. For example, the config can set `screenshot: always` and the command line can give
`--artifacts results`.

### Desktop and mobile in the same folder

The three CLIs read the same config file. Each CLI ignores the config values that it cannot use. It prints one
note on stderr with the names of these values, and then it continues:

```text
plain: desktop ignores these config values: headless, workers: 4, artifacts.trace: on-failure
```

| CLI | Config values that it ignores |
|---|---|
| `plain` | `server` |
| `plain-computer` | `headless`, `timing`, `profile`, `channel`, `cdp`, `server`, `workers` more than `1`, `timeout: 0`, an `artifacts.trace` mode other than `off` |
| `plain-mobile` | `headless`, `timing`, `profile`, `channel`, `cdp`, `workers` more than `1`, `timeout: 0`, an `artifacts.trace` mode other than `off` |

In place of an ignored value, the CLI uses its default: one worker, a `15000` ms timeout and no trace. This is
also true for `validate` and `--list`.

The same value as a command-line option stops the CLI (exit `2`), for example `plain-computer --headless` or
`plain-mobile --workers 4`. An option is a request for this run, thus the CLI does not ignore it. The
environment variables in the [order of precedence](#order-of-precedence) are not config values. A CLI that does
not use one of them ignores it and prints no note.

To give desktop or mobile specs other values, for example other `files`, use a second config file:
`plain-computer --config desktop.config.yaml`.

## Check specs without a run

```sh
plain validate tests/
plain-computer validate tests/desktop/
plain-mobile validate tests/mobile/
```

`validate` loads each file, expands the includes and checks the schema. It also checks the placeholders in the
browser `url`, the desktop `app`, the mobile `platform`, `device`, `app` and `capabilities` fields, and all step
strings:

- `${env.*}` must point to a value in the spec `env` block. Missing, null, object and list values are errors.
- A `$VAR` value counts as declared, also when the environment variable is not set. An absent variable gives a
  warning, not an error.
- `${hooks.*}` is not checked.
- Any other placeholder namespace is an error.

`validate` does not open a session, run hooks or ask for an API key. It does not check device presets, stored
browser state or hook exports. Selection options do not filter it. It prints one line for each file:

```text
✔ tests/login.yaml
! tests/secret.yaml: tests/secret.yaml: "env.password" references $TEST_PASSWORD but that env var is not set
✘ tests/broken.yaml: ${env.unknown} is not defined (use ${env.*} from the spec's env block)
```

`validate` exits with `0` when all files are valid, also with warnings. It exits with `1` when a file has an
error, and with `2` for a command or config error.

`--list` is different. It reads `$VAR` values from the environment, so the variables of each spec must be set. It
prints load errors on stderr and exits with `1`.
