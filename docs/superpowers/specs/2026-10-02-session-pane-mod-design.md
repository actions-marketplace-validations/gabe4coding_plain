# Session pane mod — design

Date: 2026-10-02. Status: approved design, not implemented.

## Goal

A Claude Code mod that draws a live pane of what the agent does through a plainwright MCP server: the page or app
it is on, the flow's goal, each step with its status and Jev tokens, and two controls — save the passing steps as a
spec, and copy the last failure. Today this information exists only as JSON inside tool results in the transcript.

It covers all three plugins: browser (`plainwright`), desktop (`plainwright-computer`) and mobile
(`plainwright-mobile`).

Non-goals for this version: screenshots in the pane, changing or blocking any tool call, the irreversible-step guard
(a separate mod), and suite runs (`/pw run`, a separate mod).

## Constraints

- Mods run only in Claude Code (CLI and the Desktop Code tab, v2.1.287+). The plugins are also Codex plugins, so the
  MCP servers stay the product; the mod is an optional layer and must never change what a tool returns.
- The Codex manifests (`.codex-plugin/plugin.json`) name `skills` and `mcpServers` explicitly and no `hooks`, so a
  `hooks/` directory in a plugin is invisible to Codex.
- A hooks module may import only files inside its plugin directory and the bare `claude-code` module.
- The pane uses only elements both the terminal and Desktop draw (`Box`, `Text`, `Button`, `Input`): no `Image`,
  `Raster` or `Svg`.
- `scripts/build-plugins.mjs` is the only writer of generated plugin files; the mod copy is generated like
  `bin/launch.mjs`.

## Approach

One mod source, copied into each plugin at build time.

```
mods/session-pane/              source of truth (not compiled by the root tsc)
  register.ts                   the hooks module
  model.ts                      pure: tool result → pane state (no mods API)
  view.ts                       pure: pane state → element tree
  session-pane.test.ts          claude plugin test
plugins/<name>/hooks/           generated by build-plugins.mjs
  hooks.json                    { "modules": ["./session-pane/register.ts"] }
  session-pane/*.ts             copied from mods/session-pane/ (tests excluded)
```

Each copy learns its own plugin from `$.plugin.name` and watches only that plugin's server. Rejected alternatives: a
fourth `plainwright-pane` plugin (an extra install, and it must guess which servers exist), and one mod in the
browser plugin matching all three prefixes (couples the plugins).

## Units

### `model.ts` — pure state

`State = { target?: string, goal?: string, rows: Row[], tokens: number, lastFailure?: Failure }`, where `target` is
the URL (browser) or app/device (native), and `Row = { kind, label, status?, tokens, detail? }`.

`apply(state, tool, args, result) → State`, one case per tool name (the suffix after the server prefix):

| Tool | Effect |
| :- | :- |
| `open` | sets `target` (result `url`, else `args.app`/`args.device`/`args.url`) and `goal` (`args.goal`). Native servers reset `rows`, as their transcript resets; the browser adds a `goto` row. |
| `step` | one row: step kind and target text from `args.step`, `status`, `jevTokens`, `detail` when not `pass`. |
| `batch` | one row per entry of `results`; steps after `stoppedAt` are not shown. |
| `ask`, `read`, `find`, `snapshot` | one dim row; `jevTokens` added to the total. |
| `save`, `close`, `evaluate`, `screenshot`, discovery tools | no row. |

A non-pass row becomes `lastFailure` with the step, status, detail, notes, url and `changed`. A result that is not
JSON, an `isError` result, or a `deny` leaves the state unchanged. The step label comes from the step object:
its one key is the kind, and the value (or its `target`/`that` field) is the text.

### `view.ts` — pure tree

`render(state, ui, { bodyColumns, saveName }) → tree`: header (target, then goal dimmed), the rows (newest at the
bottom; icon ✓ pass, ✗ fail, ? inconclusive, ! error, – skipped; tokens right-aligned; detail on its own dim line),
a footer (`N steps · P pass · T Jev tokens`), an `Input` holding the save path, and the buttons **Save as spec** and
**Copy last failure** (the second only when there is a failure). Text is truncated to `bodyColumns`.

### `register.ts` — the only file that touches the mods API

- `tool.call` with matcher `{ tool: /^mcp__plugin_<plugin>_[^_]+__/ }`: `const result = await next(e)`, then
  `state = apply(...)` in a `try` (a model or view bug must not break the tool call), `$.ui.invalidate('ui.render')`,
  `return result` unchanged.
- First successful `open`: `$.ui.open({ id: 'plainwright' })`, unless the user closed the pane in this session.
- `ui.render` with `{ component: 'Pane', requestId: 'plainwright' }`: returns `render(...)`.
- `ui.press` Save: `$.mcp.call(<server>, 'save', { path })`, then `$.ui.toast` with the saved path and step count, or
  the error. Copy: `$.ui.copy(JSON.stringify(lastFailure, null, 2))`.
- `ui.input`: keeps the edited save path. Default: the goal as a slug, else `plainwright-session`, plus `.yaml`.
- `session.start`: registers the command `/plainwright-pane` (toggle).
- `session.end`: resets the state.

The server name for `$.mcp.call` is the name `/mcp` lists (`plugin:<plugin>:<server>`); the server key is read from
the first matched tool name, so the mod does not hard-code it.

## Error handling

The mod observes only. Every failure inside it (unparseable result, rendering, a failed save) is caught: the tool
result goes back to Claude unchanged, and only the pane shows a toast. Hooks finish well under the 10 s limit (no
waiting besides `next` and `$.mcp.call`).

## Testing

- `mods/session-pane/session-pane.test.ts`, run by `claude plugin test`: fire `tool.call` with stubbed plainwright
  results (pass, inconclusive batch stopping at index 1, native `open` reset, a non-JSON result), check the rendered
  tree, press Save and check the `mcp.call` arguments, check the result Claude receives is byte-identical.
- `npm run test:mods`: opt-in (needs the `claude` CLI); `npm test` is unchanged.
- Manual: `claude --plugin-dir plugins/plainwright`, drive `examples/` sites, in the terminal and the Desktop app.

## Open checks (first implementation step)

1. The exact tool-name prefix and `/mcp` server name for a marketplace install and for `--plugin-dir`.
2. That `claude plugin validate --strict` accepts the generated `hooks/` in each plugin.
3. That the mod sources stay out of the root `tsconfig.json` build and out of `runtime.tgz`.
